# Autoexec behavior

Background for how configs get executed automatically. Verify changes against sources listed per row.

## Engine startup (ET: Legacy, all mods)

`src/qcommon/common.c`: `default.cfg` → `profiles/<profile>/etconfig.cfg` → `exec autoexec.cfg`.

`autoexec.cfg` is resolved through the mod's search path (`~/.etlegacy/<mod>/`), which is why each mod gets its own symlinked `autoexec.cfg` (= `default/mods/<mod>/autoexec.cfg`). `etconfig.cfg` is regenerated by the game ("do not modify") — persistent settings belong in `cvars.cfg`/binds files.

## Event autoexecs per mod

All event files are looked up in the mod search path (hence `deploy.sh` links `default/autoexecs/*` into the mod folder). Missing files are silently skipped. Filenames are case-sensitive on Linux.

Details for legacy (source-verified):
- Map load: `autoexec_<mapname>.cfg`, else `autoexec_default.cfg`. With `sv_cheats`: `autoexec_devmap_<map>.cfg` / `autoexec_devmap_default.cfg` first, falling back to the normal files.
- On respawn (not revive): class file if class changed, then team file if team changed.
- `vid_restart` restarts the cgame (`src/client/cl_main.c` `CL_Vid_Restart_f` → `CL_InitCGame`), and `CG_Init` runs the map/default file again. So they also run on every `vid_restart` (e.g. `ta_Axis`/`ta_Allies` in `scripts/classcript.cfg`), not only on map load.
- The exec is queued (`trap_SendConsoleCommand`), so when `vid_restart` is called from an alias, the autoexec runs *after* the rest of that alias. A `reset <hook>` in an autoexec therefore re-arms a run-once hook that just disabled itself.
- Other mods: whether their cgame re-runs map autoexecs on `vid_restart` is unverified (likely, as the file is exec'd from cgame init).

## Two passes: definitions and state

`mods/<mod>/autoexec.cfg` runs `unbindall`, then `definitions.cfg` (the general files plus the mod's `mod_general.cfg` and `mod_classcommands.cfg`), then `profiles/user.cfg` (personal settings: name, fps, mouse, fov, refresh rate, fullscreen resolution, network rates; not in version control, a missing file only prints `couldn't exec`), then `default/state.cfg` (start values of everything scripts change at runtime; it ends with `vstr modState`, the mod's own state, defined in `mod_general.cfg`). `state.cfg` applies aliases that `user.cfg` may redefine (`fullscreenResolution`, `netNormalRates`).

- `F3` runs `vstr reloadDefinitions` (defined in `definitions.cfg`), so only the definitions and `user.cfg`. Toggles, class binds, team and brightness survive.
- `F1` runs `exec autoexec.cfg`: full reset, for a server switch within the same mod (which scripts cannot detect).
- A mod switch goes through `autoexec.cfg` as well, so it resets state.
- Which state resets on `F3` is a per-feature decision (`.claude/rules/exec-chain.md`).

## How this repo uses them

- `default/autoexecs/` holds map autoexecs (mostly spawnpoints) plus team files; linked for `AUTOEXEC_MODS="legacy etpub silent etjump nitmod"` in `deploy.sh` (every mod with event autoexecs). etpub, silEnT and ETJump run the chain with the general default values (`default/mods/<mod>/`, not tested in game).
- `default/mods/legacy/autoexec_default.cfg` sets `spawnSelectorMap "spawnmenu"` (legacy spawn menu on maps without map file); `default/autoexecs/autoexec_default.cfg` (etjump, nitmod) sets `"vstr spawnSelector3"`. The latter execs `scripts/spawn/generic_spawnpoints.cfg` (generic menu); legacy's own spawn menu needs no list. `default/mods/etpub/autoexec_default.cfg` and `default/mods/silent/autoexec_default.cfg` set no spawnpoints, because etpub and silEnT run it after the map file (maps without map file keep the previous map's spawnpoints there); they only exec `autoexec_mod.cfg`.
- Spawnpoint aliases (`spawnp*`, `echosp*`, `spawnsay*`, `spawnpsr/-psb`) survive map and mod changes (switching `fs_game` only re-execs `etconfig.cfg`, `src/qcommon/files.c` `FS_Restart`). So every map autoexec defines its own menu: `spawnpsr`/`spawnpsb` hold the echo list and the binds of exactly that map's keys, and the spawn selector unbinds all layer keys before it runs them (`spawnSelector3`, `scripts/spawnscript.cfg`). Aliases of a previous map with more spawnpoints stay defined but are on no key. `scripts/spawn/generic_spawnpoints.cfg` (generic menu, 7 keys) is only exec'd where no map menu exists: by `default/autoexecs/autoexec_default.cfg`.
- Mod switch: switching `fs_game` does not re-exec `autoexec.cfg`, so the previous mod's values (`setTeamSpectator`, weapalt binds, class command IDs, nitmod `chat_shortcuts.cfg`) would stay until `F3`. Every map autoexec and `autoexec_default.cfg` therefore starts with `exec autoexec_mod.cfg` (`default/mods/<mod>/autoexec_mod.cfg`, symlinked as `autoexec*`). Guard: `mods/<mod>/autoexec.cfg` sets `modLast "vstr modIs_<mod>"` and `modIs_<mod> "exec autoexec.cfg"`; `autoexec_mod.cfg` sets its own `modIs_<mod>` to `vstr null`, runs `vstr modLast`, then re-arms it. So `autoexec.cfg` runs only if another mod's chain was loaded last, never on a normal map load or `vid_restart`. A mod without `mods/<mod>/autoexec_mod.cfg` just prints `couldn't exec autoexec_mod.cfg`; `vstr` on an undefined cvar is a no-op (`src/qcommon/cmd.c` `Cmd_Vstr_f`), hence the armed `modIs_<mod>` in the chain.
- jaymod runs no event autoexecs, so `spawnSelectorMap` stays empty and ENTER does nothing there.
- Mod dispatch: `definitions.cfg` execs `mod_general.cfg` and `mod_classcommands.cfg` by bare name, so the mod search path picks the current mod's file (`deploy.sh` links them into `~/.etlegacy/<mod>/` like the autoexecs). `FS_AddGameDirectory` prepends the pk3s first and the mod directory last (`src/qcommon/files.c`), so a loose file in the mod folder wins over every pk3, and the pure-server restriction for directories explicitly allows `.cfg`. Mods without `default/mods/<mod>/autoexec.cfg` never run the chain.
